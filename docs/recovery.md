# Recovery and lifecycle

**Default rule: keep the held writer excluded when evidence is incomplete.** No “reset state,” copy-and-replay, new-worker redispatch, fallback model, or unsafe stale-lock clearing is part of this integration. The cost of avoiding duplicate provider/tool/issue effects can be an indefinitely unavailable workspace. Do not run this procedure on another deployment's database, WAL, worktree or prior run state.

## Normal operation and stop

The standalone BFF serves one operator-owned, private `stateRoot`; only one BFF may own it. A graceful `SIGINT`/`SIGTERM` starts coordinator shutdown and attempts to settle owned work; the BFF frees the owner lock only on orderly close. Stop accepting new issue wakes at the Paperclip host before maintenance, then wait for **actual provider, worker, descendant and governed-effect settlement** and confirm the host's physical writer exclusion has been released for those runs. A stopped local process does not itself prove a remote provider/effect stopped. An adapter cancellation sends a purpose-bound original-owner DELETE; a response is release proof only when it reports the correlated settled outcome. Do not use process termination as a replacement for cancellation/settlement.

A BFF restart reconciles admitted/running/approval-wait operations as **uncertain** and retains their leases. An HTTP stream interrupted after acceptance also remains uncertain unless a matching terminal or original-owner stop proof exists. Operator observation may retrieve events or initiate reconcile only through the original signed run/control authority; endpoints are not open maintenance tools. The worker must not resume or repeat uncertain provider, MCP or issue-finalization requests. The host independently retains physical writer exclusion for unknown and settled Prime provenance: even a later non-Prime agent in another company cannot automatically write to an overlapping root.

The live qualification sequence is **unresolved**, not a successful subscription run. Early fresh canaries failed at catalog startup and retained their holds. A later run authenticated the exact catalog model and native Prime accepted its session, but its first provider request returned an uncertain receipt with no response ID. The host then refused a separate scope before provider work because the earlier account owner remained unresolved. Lack of observed output, local termination or elapsed time is not settlement evidence.

Do not create new issues/workspaces or clone credentials to evade that account fence. Preserve both account ownership and physical-writer holds. Further qualification requires original-owner settlement or a separately authorized distinct subscription; there is no automatic credential fallback. Controlled native tests confirmed that uncertain MCP cancellation retains the writer, while settled children and original approval/rejection receipts can be correlated. Those fixtures do not release any live hold.

## After an unclean exit or a stale owner lock

`prime-owner.lock` includes a PID/start timestamp and is deliberately left after an unclean exit. `EEXIST` means either the old BFF still owns the state or its exit is quarantined. Investigate **out of band** using trustworthy process/service-manager and host/BFF run records: establish that no old BFF, contained worker, descendant, provider request or governed effect can still write; correlate each accepted request with provider/effect/worker settlement evidence and host physical-writer state. Also inspect the assigned workspace for other live writers. A reused PID, absent process, elapsed deadline, local `SIGKILL`, clean-looking SQLite file, or a missing provider receipt alone is not sufficient.

Only after an operator has independently established that the old process is gone **and** decided to quarantine any still-uncertain operation and preserve both host and BFF writer exclusion may the operator consider clearing that owner lock using their normal controlled incident procedure. This is **not** permission to clear a physical writer hold or mark a provider/effect “settled.” There is no public automatic stale-lock sweeper, unsafe reset/replay endpoint or trust-promotion API. If the facts cannot be established, leave the lock and workspace fenced and investigate with the provider/tool owners instead of starting another writer. Never edit the BFF SQLite/WAL or host authority tables to force admission.

## Checkpoints and backups

Back up **the host database, BFF private state including SQLite/WAL and immutable checkpoint tree, and the workspace** consistently, preserving permissions and provenance. BFF state and Paperclip host state are separate but correlated by run/receipt; restoring only one side does not establish settlement or enable a session. Native checkpoints are immutable, digest-checked and bound to same company/agent/issue/namespace/workspace/model/connection and settled terminal receipt. If one is lost or corrupt, halt: do not make a new session to conceal the loss, replay old Python cells, restore arbitrary process RAM, or copy a transcript from a different run. The repository stores private state; the workspace stores files; neither is an interchangeable replacement for the other.

## Upgrade, rollback and uninstall

Treat the host revision, host migration, adapter/BFF protocol, native binary, native catalog, Python lock and built runtime digests as **one compatibility set**. Before changing binaries: stop new admissions, preserve complete state and receipts, allow active operations to settle or remain fenced, then build a **new** runtime root from pinned sources and set its exact emitted hashes in a new private BFF config. Do not modify an in-use runtime tree; do not point an old host/BFF at newer checkpoints/migrations. Requalify a new release with a fresh disposable state and a separately authorized provider-consuming run. A rollback is only valid when that older set can safely read the retained state/schema and every held writer remains excluded; otherwise keep the newer state isolated and do not dispatch. Disabling `prime_bff` on future agents or uninstalling the external adapter does not settle existing effects, release old writer locks, or make the workspace safe for another adapter. Retain incident evidence and restore normal non-Prime access only where the physical provenance policy permits it.
