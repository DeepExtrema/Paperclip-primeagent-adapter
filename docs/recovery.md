# Recovery and lifecycle

**Default rule: keep the held writer excluded when evidence is incomplete.** No “reset state,” copy-and-replay, new-worker redispatch, fallback model, or unsafe stale-lock clearing is part of this integration. The cost of avoiding duplicate provider/tool/issue effects can be an indefinitely unavailable workspace. Do not run this procedure on another deployment's database, WAL, worktree or prior run state.

## Normal operation and stop

The standalone BFF serves one operator-owned, private `stateRoot`; only one BFF may own it. A graceful `SIGINT`/`SIGTERM` starts coordinator shutdown and attempts to settle owned work; the BFF frees the owner lock only on orderly close. Stop accepting new issue wakes at the Paperclip host before maintenance, then wait for **actual provider, worker, descendant and governed-effect settlement** and confirm the host's physical writer exclusion has been released for those runs. A stopped local process does not itself prove a remote provider/effect stopped. An adapter cancellation sends a purpose-bound original-owner DELETE; a response is release proof only when it reports the correlated settled outcome. Do not use process termination as a replacement for cancellation/settlement.

A BFF restart reconciles admitted/running/approval-wait operations as **uncertain** and retains their leases. An HTTP stream interrupted after acceptance also remains uncertain unless a matching terminal or original-owner stop proof exists. Operator observation may retrieve events or initiate reconcile only through the original signed run/control authority; endpoints are not open maintenance tools. The worker must not resume or repeat uncertain provider, MCP or issue-finalization requests. The host independently retains physical writer exclusion for unknown and settled Prime provenance: even a later non-Prime agent in another company cannot automatically write to an overlapping root.

The earlier live qualification holds remain **unresolved**, even though a later separately authorized new-work acceptance succeeded. An earlier canary authenticated the exact catalog model and native Prime accepted its session, but its first provider request returned an uncertain receipt with no response ID. Its host credential-owner marker initially blocked other agents sharing the same company/OpenAI account, even though their configurations were unchanged. An explicitly authorized audit subsequently proved that one host credential lease settled and archived only its marker. Two account-only admission/cleanup cycles then succeeded with HTTP dispatch forbidden. Its provider/worker/workspace uncertainty remained unchanged.

Do not create new issues/workspaces or clone credentials to evade an unresolved **credential** owner. The repaired host distinguishes credential-owner settlement from provider outcome; this does not weaken writer exclusion or permit replay. Controlled cancellation/approval fixtures do not release live holds.

A later, separately approved diagnostic reached an HTTP 200 provider response, then failed the host's MIME-only admission check before reading any provider events. Current source removes that additional gate and validates the actual SSE receipts, as the native client does. The lost body and exact media subtype were not retained; this is not proof of provider completion and cannot retroactively settle either that request or another held run. A stopped local worker also does not establish provider settlement. Retained BFF leases exclude the same agent or issue as well as overlapping roots; another directory is not a way to restart a held agent.

The bounded live acceptance on 2026-10-10 UTC does not settle any earlier run. A preceding new-work task completed provider requests, Python execution and its evidence document, and its BFF terminal settled/released the native lease, but host finalization was rejected with HTTP 422 because the test omitted a required review path. That host finalization/workspace hold remains. The successful task used a separate issue and non-overlapping workspace after native/provider settlement, with no retained BFF agent lease; it did not replay the rejected finalization or clear its hold. Do not generalize this to a run whose provider, worker or BFF agent lease remains unresolved. The public integration still has no generic recovery/reset endpoint.

## “Automatic recovery stopped” in the task UI

This is a **recovery disposition, not the original failure diagnosis**. The host cannot establish that another attempt would avoid repeating an unverified action. Even a setup-looking error is not positive proof that provider work never started; current classification uses recorded execution evidence, not error-message matching. An external adapter's run can have host runtime mode `legacy` without describing the adapter's own internal runtime.

Use **Inspect run** in the recovery banner to read the original failure. The banner preserves the server's next-action guidance and deliberately does not offer a generic Retry. A recovery record marked `resolved` can still carry `automaticRecovery.replay = "blocked"`: the automatic recovery procedure finished, but execution permission was not restored.

This does not remove supported evidence-gated continuation elsewhere. Qualified conversation/native-runner paths can admit an explicitly authorized fresh turn after verifying the exact source, stopped execution, cleanup, history and current task policy, without declaring unknown old outcomes successful. Other adapters and unresolved provider/workspace/finalization holds require their supported incident-specific reconciliation. Do not clear a hold, switch adapters or invent bootstrap/termination evidence to make Retry succeed.

## Proven non-admission after a terminal

The existing `POST /internal/paperclip/prime-runs/:operationId/reconcile` accepts an optional JSON body `{ "terminalReceiptId": "...", "request": <original complete broker envelope> }`, bounded to 16 MiB. This is an original-owner proof operation, **not a retry**: the original Paperclip PUT is never forwarded. Both the run header and the original, unexpired sealed control capability are required. An execute token, replacement authority, HTTP 403, elapsed deadline, absent PID or aggregate `operation.status` is insufficient.

Use this path only after fixing the cause and preserving the individual incident's evidence:

1. Bind the original complete envelope to its retained uncertain IPC row by canonical SHA-256. Require the original accepted session and unique uncertain terminal, positive provider settlement and stopped worker/descendant evidence, no checkpoint or finalization, and no currently owned worker/dispatcher.
2. The host's control-only `effect.non_admission` serializes with admission under the original authority lock. It requires a stopped fence, all admitted effects settled, and no target request row or owned target dispatch. It durably records the exact request ID, full-envelope digest and authority before returning proof. This assumes the original ledger has not been pruned, restored or tampered with.
3. The BFF requires no other unresolved IPC row. Schema 32 adds append-only reconciliation and host-handoff tables; it atomically records the proof and releases only this operation's matching BFF writer. The original IPC response, terminal, receipt sequence, outcome and checkpoint remain unchanged. A replacement terminal is independently rejected by the repository.
4. The BFF requests `operation.reconcile_worker` using a deterministic observation ID. The host validates its original persisted failed terminal, full session identity, stopped-worker evidence, durable non-admission proof, absent live actor and absent finalization ambiguity. Under the physical-admission lock it records proof, settles the worker and releases only the matching host physical writer. The proof's `terminalDigest` hashes the complete **host adapter result**, not the BFF terminal. Independently verify both digests and the unchanged original ledgers.
5. A null `hostHandoff` means only the BFF side completed; host exclusion remains. An identical authenticated observation may finish that handoff without redispatching the PUT. Do not create a different agent or workspace to evade it.
6. Paperclip's separate issue-level no-replay disposition may still block a new run after both writers settle. Use the existing board-only `/api/issues/:id/recovery-actions/resolve` contract for the **exact** recovery action and original run, recording `providerStopped: true` and the observed action outcomes with the durable proof references. Distinguish completed reads/provider work from a never-admitted write. This supported transition queues one fresh-session continuation; it does not replace the original failed run. Do not issue a second wake while its durable delivery is pending.

The live incident smoke preserved seven original host requests, 4,085 host receipt frames, eight native receipts and eight IPC rows, including the rejected PUT and failed/null-checkpoint terminal. It appended two host proofs and one BFF reconciliation, released only that incident's writers, and returned the same receipt on repeated observation. Earlier provider-unknown and host-finalization holds remain unresolved.

Rebuild the current host patch **and BFF** for this path; the original `v0.1.0` artifacts do not contain it. Wire protocol v3 and the attested native image are unchanged. There is no generic reset, automatic uncertain-effect replay, provider-unknown recovery, expired-control replacement or retroactive successful checkpoint.


## Host credential-owner recovery

The current host patch closes credential admission and drains its catalog/stream scopes before managed-account cleanup, independently of remote provider outcome. Cleanup still refuses an OAuth refresh fence or unconfirmed rotation. The `v0.1.0` source tag predates this repair; rebuild the pinned host with the current complete patch. Adapter/BFF 0.1.0, wire protocol, database schema and native runtime are unchanged by this host-only correction.

A stale account-owner marker is **not** automatically removable. Any exceptional recovery requires explicit operator authorization and evidence for the individual marker:

1. Correlate the exact marker with its Prime run, grant, original host PID/start identity and credential-custody contract. New markers record company, agent, run and adapter identity; older markers need independent run/service evidence. A timestamp or missing process alone is insufficient.
2. Establish that this run used the host-only Prime credential path and that no original host credential scope can still use or rotate the account. A worker's continuing or unknown computation is not credential ownership when it never received credentials.
3. Establish refresh settlement: no unresolved durable OAuth fence, unmatched rotated credential or unconfirmed secret commit. Preserve the fence, restricted home and account exclusion if any of this is unknown.
4. Serialize the transition with the existing account admission gate, revalidate the exact marker bytes and owner set, and archive only that authorized marker with private evidence. Retain its restricted home. Do not sweep other owners or clear a stale admission gate speculatively.
5. Verify account admission/cleanup without provider dispatch and verify the original provider, worker, governed-effect and host/BFF writer holds remain unchanged. Do not change run outcomes, delete authority/lease rows, edit SQLite/WAL or initiate a retry as part of credential recovery.

This is a credential-only incident procedure, not a reset endpoint or general stale-lock policy. If individual attribution or refresh settlement cannot be proven, leave account admission fenced. A distinct separately authorized subscription remains an alternative, not an automatic fallback.


## After an unclean exit or a stale owner lock

`prime-owner.lock` includes a PID/start timestamp and is deliberately left after an unclean exit. `EEXIST` means either the old BFF still owns the state or its exit is quarantined. Investigate **out of band** using trustworthy process/service-manager and host/BFF run records: establish that no old BFF, contained worker, descendant, provider request or governed effect can still write; correlate each accepted request with provider/effect/worker settlement evidence and host physical-writer state. Also inspect the assigned workspace for other live writers. A reused PID, absent process, elapsed deadline, local `SIGKILL`, clean-looking SQLite file, or a missing provider receipt alone is not sufficient.

Only after an operator has independently established that the old process is gone **and** decided to quarantine any still-uncertain operation and preserve both host and BFF writer exclusion may the operator consider clearing that owner lock using their normal controlled incident procedure. This is **not** permission to clear a physical writer hold or mark a provider/effect “settled.” There is no public automatic stale-lock sweeper, unsafe reset/replay endpoint or trust-promotion API. If the facts cannot be established, leave the lock and workspace fenced and investigate with the provider/tool owners instead of starting another writer. Never edit the BFF SQLite/WAL or host authority tables to force admission.

## Checkpoints and backups

Back up **the host database, BFF private state including SQLite/WAL and immutable checkpoint tree, and the workspace** consistently, preserving permissions and provenance. BFF state and Paperclip host state are separate but correlated by run/receipt; restoring only one side does not establish settlement or enable a session. Native checkpoints are immutable, digest-checked and bound to same company/agent/issue/namespace/workspace/model/connection and settled terminal receipt. If one is lost or corrupt, halt: do not make a new session to conceal the loss, replay old Python cells, restore arbitrary process RAM, or copy a transcript from a different run. The repository stores private state; the workspace stores files; neither is an interchangeable replacement for the other.

## Upgrade, rollback and uninstall

Treat the host revision, host migration, adapter/BFF protocol, native binary, native catalog, Python lock and built runtime digests as **one compatibility set**. Before changing binaries: stop new admissions, preserve complete state and receipts, allow active operations to settle or remain fenced, then build a **new** runtime root from pinned sources and set its exact emitted hashes in a new private BFF config. Do not modify an in-use runtime tree; do not point an old host/BFF at newer checkpoints/migrations. Requalify a new release with a fresh disposable state and a separately authorized provider-consuming run. A rollback is only valid when that older set can safely read the retained state/schema and every held writer remains excluded; otherwise keep the newer state isolated and do not dispatch. Disabling `prime_bff` on future agents or uninstalling the external adapter does not settle existing effects, release old writer locks, or make the workspace safe for another adapter. Retain incident evidence and restore normal non-Prime access only where the physical provenance policy permits it.
