# Configure one managed Prime agent

`prime_bff` is an explicit **per-agent** adapter choice in a patched Paperclip host. Installing it does not change a company default, other agents, or the behavior of Pi, OMP, Codex or any other adapter. Configure it only for a new issue with a responsible user permitted to select the OpenAI subscription connection and a separately prepared local workspace. A previously saved task session cannot be transparently transferred from another adapter or another model/connection/workspace.

For a company requiring formal agent-hire approval, the new canary must go through `POST /api/companies/:companyId/agent-hires` and normal board approval; a pending agent cannot run. Only companies permitting direct creation may use `POST /api/companies/:companyId/agents`. Neither installation nor approval changes the company's hiring policy, other agents or its default adapter; see [install](install.md#3-register-without-changing-defaults).

## Adapter and connection

The adapter's `getConfigSchema()` exposes:

| Agent field | Meaning |
| --- | --- |
| `bffBaseUrl` | Credential-free loopback HTTP origin of the standalone BFF, e.g. `http://127.0.0.1:4319`; no path, query, fragment or embedded userinfo. |
| `cwd` | Existing dedicated workspace path in the host's project/execution-workspace configuration. Host final authority, not a path supplied by the worker, determines the real root. |
| `model` | Exact host-selected subscription model. Initial managed profile: `gpt-6.1-sol` under provider `openai-codex`. Mismatch with the host's selection fails before dispatch. |

The host also needs the agent's **explicit `aiConnection` binding** to an eligible, granted OpenAI **subscription** connection. Its own credential lifecycle refreshes and owns subscription auth; the worker gets neither the grant's bearer nor a `CODEX_HOME`/`OPENAI_API_KEY` credential. API-key binding, arbitrary Prime provider IDs, silent fallback or accepting a catalog entry merely because it is present in a static file are not this profile. Host authority checks the selected account and authenticated model catalog per run and again on broker dispatch; if the account or selection changes, dispatch is refused. The native catalog patch supplies Prime-side model capability/limits metadata, not an account entitlement. Selection binds root, children and compaction to the same model; native max child depth is **2**, max children created **4**.

In the agent's `runtimeConfig.aiConnection`, the host's strict binding schema accepts `{"provider":"openai","method":"subscription","mode":"responsible_user"}` (the responsible user's permitted default determines the **actual** selected method). Shared mode instead requires exactly `provider` = `openai`, `method` = `subscription`, `mode` = `shared`, and real host-issued UUID values for `connectionId` and `grantId`. Do not invent grants or put credentials in this JSON. A legacy `delegated` wire mode exists, but new UI does not create it. The host validates the actual selected subscription, active matching grant/install, account health and assigned model on admission. Local adapter registration and agent creation were exercised **without** a configured binding and did not prove account connectivity or dispatch.

`testEnvironment` calls the BFF's credential-free `GET /internal/paperclip/prime-runs/capabilities` with a short timeout and reports availability/protocol, plus a warning that authenticated catalog/connection validation happens at managed run admission. It does **not** perform a provider call or establish that `gpt-6.1-sol` is currently available to the selected account. Unsupported connection or model must fail closed; don't fix it by substituting an API key or different default model.

The corrected host subscription OAuth parser accepts a credential JSON object's `OPENAI_API_KEY:null` alongside its subscription token and account fields; `null` is **not** an API key and does not authorize API-key billing or export a provider secret into the worker. Host no-owner UUID filtering has also been corrected without weakening physical writer exclusions or retained uncertain holds. Focused host tests including real PostgreSQL cover these fixes, not a successful authenticated live Prime run.

## Workspace profile

Preprovision a **dedicated, already existing project and execution workspace**, with one known canonical local root; explicitly associate the assigned issue with that workspace and ensure it is active. Give the selected agent only the intended read/write scope and keep unrelated repositories, other companies' roots, other processes' mutable writers, private homes and the BFF state outside it. A workspace alias, overlapping root, unsafe path, unexpected Git worktree metadata, secondary repository, runtime service, setup/provision/restore command, isolated task directory, remote target or fallback agent cwd is rejected in the patched host. Host Git/worktree operations are deliberately disabled for Prime; the native contained Python/kernel can read/write its authorized workspace and run code/Git **inside** the sandbox. Existing external worktree Git directories must not be mounted into it.

Read-only resources and *assigned* Paperclip-managed skills are separately materialized, content-attested and mounted into the worker; unavailable/mutated skill sources fail admission. Only the explicit managed instructions bundle and task prompt reach the worker. Prime's ambient home/extensions/skill discovery, autonomous schedules, refinement and unrelated MCP connectors are not enabled. Choose explicitly authorized Paperclip MCP assignments with a scoped `gateway_only` binding; the host snapshots tool schemas and checks actor/connection/gateway policy again at use. The agent cannot mint new tools from prompts. An approval waits on the actual original invocation: allow, formal approval or denial is reconciled against the same effect identity, not executed a second time under a fresh tool call.

## Run behavior and issue status

Start an assigned issue run through Paperclip's ordinary issue workflow. Paperclip issues separate execute/control capabilities only after the final host realization, records the operation and workspace exclusion, and supplies the approved prompt, instructions, skills and MCP set. A BFF POST uses those capabilities; do not call it with a fabricated token or send a generic agent bearer to the worker. The broker streams Prime events, including model usage and governed tool receipts. Native `finish` is an **intent** to mark the assigned issue `blocked`, `in_review` or `done`; the host commits status only after the settled terminal and its ordinary actor/artifact authorization gates. Unknown status of a finalization is fenced, not retried blindly. A completed settled turn persists a scoped checkpoint; the next turn resumes only that committed state. The BFF cannot reissue an uncertain provider or tool effect just to make a run succeed.

See [architecture](architecture.md) for the boundary map and [recovery](recovery.md) before stopping or upgrading the BFF. The configuration described here is source-backed; [installation](install.md) distinguishes offline evidence from actual authorized provider qualification.
